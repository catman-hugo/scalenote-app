# Version 0.2 plan: editor completion

Goal from the spec: finish the editor so notes can be written for real, and add the settings and the update notice. Each slice is built on its own branch, tested, and merged by the owner before the next one starts.

Rules that apply to every slice (from `CLAUDE.md`): unknown markdown is kept byte for byte, every text goes through `web/strings.js`, writes are atomic, nothing is called done without being tried, and each slice ends with screenshots in light and dark.

## Slice 0.2.1: text formatting and simple blocks
- Bold, italic, strike, inline code and links get a small toolbar and shortcuts (they already round-trip).
- Underline, highlight, text colour, sub and superscript. Markdown has no syntax for these, so they are stored as inline html (`<u>`, `<mark>`, `<sub>`, `<sup>`, `<span style>`), which Obsidian shows too. Decision needed before building: the splitter now treats any `<...>` as raw, so these tags need an allow-list that the editor can read and write.
- Callouts in Obsidian's format (`> [!note] Title`), currently raw blocks.
- Toggles (`<details><summary>`), currently raw blocks.
- Tables in standard markdown pipe format, currently raw blocks.

## Slice 0.2.2: images and attachments
- Paste, drop or insert an image. The file is copied to `attachments/` in the vault and referenced as `![[name.png]]` or `![](attachments/name.png)` (decision needed: which form; Obsidian reads both).
- Size limits, allowed types (png, jpg, gif, webp; SVG is not allowed because it can carry scripts), and a calm message for anything else.
- Tauri command to write binary files atomically.

## Slice 0.2.3: block gutter
- Handle at the left of each block: drag to reorder, "turn into", duplicate, delete, copy block link (needs the `^block-id` convention, which the splitter currently keeps raw).
- Must work with touch and pen, not only a mouse.

## Slice 0.2.4: markdown source view
- Toggle that shows the whole note as plain markdown and lets it be edited as text. Switching back re-parses. Because of the byte-for-byte rule, saving from source view writes exactly what is in the box.

## Slice 0.2.5: themes and settings
- Settings screen: theme (light, dark, system, plus the named themes from the spec), font size, editor width, sidebar width.
- Colours stay solid; no gradients. Theme files are data, so community themes can come later (2.1).

## Slice 0.2.6: update notice and "What's new"
- The app checks for a newer release and shows the version, date and notes. The default (off or on) is an open question for the owner, because it makes a network request.
- The check only reads a public release list and never sends vault data. The version comes from release notes, which are treated as untrusted text (no html, no links that run anything).

## Slice 0.2.7: converter for the V1 notes
- One-off tool that reads the old app's database and writes a vault: notes become `.md`, images go to `attachments/`.
- Blocked until the owner provides a copy of the old data or its format. Nothing is guessed. The converter must be tested on fake data only in this public repository.

## Order and open questions
Suggested order: 0.2.1, 0.2.2, 0.2.4, 0.2.3, 0.2.5, 0.2.6, 0.2.7. The source view comes before the gutter because it is a safety net while the other blocks are new.

Questions for the owner:
1. Update check on by default or off by default?
2. Image links: `![[name.png]]` (Obsidian style) or `![](attachments/name.png)` (standard)?
3. Which themes, besides light and dark, matter first?
4. For the V1 notes converter: can a copy of the old database be provided somewhere it can be read, with a few private notes removed?
