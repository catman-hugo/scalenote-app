# Version 0.5 plan: sync between your own devices

Written 2026-11-13 at the owner's request. The owner wants two devices of the same person to be connected in 0.5, preferably the way LocalSend works (devices on the same network see each other, and nothing needs a server), with a home server as the fallback.

## The idea in one paragraph

There is **one sync engine**, and it works between two devices that are both on. A "device" is the desktop or phone app, or a small always-on program on the home server. The server is not a different system: it is a device that never sleeps, so the same protocol, the same checks and the same tests cover every case. Two apps on the same Wi-Fi find each other like LocalSend does and sync directly. When one of them is the home server, the others reach it by typed address (home network or Tailscale) and the server keeps a copy while the laptop and phone are off.

## Can a LocalSend-style sync be done? Yes, with these limits

| Question | Answer |
|---|---|
| Windows and Linux app finding each other | Yes. The Rust side can send and listen for a small multicast announcement on the local network and run a small HTTPS server. Windows will ask once to allow the app through its firewall. |
| Android app finding other devices | Yes, but it needs a native piece (Android only lets an app hear multicast when it holds a "multicast lock"). That Kotlin code can only be compiled by CI, so it is tried on the real phone and tablet before 0.5 is called done. |
| Android syncing in the background | Not reliably. Android stops background work to save battery. In 0.5 the phone syncs while the app is open, and on a button press. Sync while the app is closed is a later improvement. |
| The browser client | It cannot find devices and cannot listen, so it can only talk to a home server (or a desktop app) at an address you type. This is why the server is needed for the browser client, and why the browser client comes last. |
| Wi-Fi that blocks devices from seeing each other (guest networks, some routers) | Discovery fails there. The fallback is typing the other device's address and port, which also works over Tailscale. |
| Both devices on at the same time | Required for direct sync. If the other one is off, nothing happens and nothing breaks; it syncs when both are on again. The home server removes this limit. |

## What stays the same

- Notes stay plain markdown files in an ordinary folder that Obsidian can open. SQLite or any index is only a cache that can be rebuilt.
- Nothing received from another device is trusted: size limits, nothing executed, paths checked so a file can never land outside the vault, and a damaged answer changes nothing.
- Keys live in the system's secure storage, never in the vault, logs or repository.
- Every write to the vault is atomic. Killing the app in the middle of a sync must not corrupt a note.
- No personal data in the repository: tests use `alice` and `bob` and `example.local`.

## Decisions to record when the slices are built

- **Conflicts never lose text.** If the same note changed on two devices since the last sync, both versions are kept: the newer one stays as the note and the other is saved next to it as "Name (conflict, device, date).md". Nothing is merged silently.
- **Deleting is a move to the trash on the other device**, never a silent permanent delete.
- **Pairing uses a one-time code** shown on one device and typed on the other. After that the two devices pin each other's keys. A device that is not paired is never synced with.
- **What is synced:** pages, attachments, drawings (`*.canvas.json`), and the hidden `.scalenote` settings that belong to the notes (folder and page colours). Not synced: the device's own settings (theme, text size), page history, and the trash of another device. The page history and trash can be added later.

## Schedule

Each row is a release the owner can try on devices. Each one follows the rules of `CLAUDE.md`: its own branch and pull request, tests that call the real functions, release notes in the short style, security checklist.

| Version | What is added | How it is checked |
|---|---|---|
| 0.5.0 | **Foundations, no network.** A list of what each file looked like at the last sync (path, size, content hash), a device id, the rules for what counts as changed, added, deleted or conflicting, and the conflict copy naming. All in `scalenote-core` (Rust), plus the Settings tab "Sync" showing only the device name. | Tests with real folders: every case of change on one side, on both sides, delete against edit, renamed folders, huge file names, symlinks, a note killed mid-write. |
| 0.5.1 | **Identity and pairing.** Each device gets a key pair kept in secure storage. A one-time pairing code and a trust list ("Paired devices", with Remove). The device listens for sync requests on a local HTTPS port only when sync is switched on. Off by default. | Tests that a wrong code, an old code, a copied code and an unpaired device are all refused; the key never appears in a log or in the vault. |
| 0.5.2 | **Finding each other.** A small multicast announcement on the local network (like LocalSend) and a "Devices nearby" list in the Sync tab. A typed address and port as the fallback. | Tests for the announcement format (size limit, junk ignored, no names of other people on the network trusted). Desktop and Android tried on real devices. |
| 0.5.3 | **The sync itself, between two apps.** Exchange of the file lists, transfer of the changed files only, atomic apply, conflict copies, deletes to trash, a progress line and calm errors. "Sync now" button and automatic sync when a paired device appears (a setting). | Two real app instances in tests syncing a real folder; interruption tests (connection cut, app killed); large vault and large attachment tests; limits on file size and file count. Desktop to desktop first. |
| 0.5.4 | **Android.** The multicast lock, sync while the app is open, a sync button, and a clear message when Android has put the app to sleep. Phone and tablet both tested. | Only a real phone and tablet can show this; CI compiles it. The owner tests: edit on each device, sync, check both. |
| 0.5.5 | **Home server.** The same sync engine as a program without a window (`scalenote-server`) for Linux on the home server, started by the system, with a small config file and an install guide. It is a paired device that is always on. Reachable on the home network and over Tailscale by address. | Run for days against the real laptop and phone; restart, power cut and disk-full tests; the program refuses to start if its data folder is not private to it. |
| 0.5.6 | **Browser client.** The web app served by the home server, signing in by pairing. It reads and writes through the server. | Security review of everything the browser can ask for (paths, sizes, request rates, cross-site requests), and the web build tried in a real browser. |
| 0.5.7 | **Hardening and release of 0.5.** Everything above on all devices at once, the security checklist for the whole 0.5 line, a plain "how to set it up" guide, release notes. | Full test runs on Windows, Linux and Android; the owner's multi-day test. |

0.6 follows as planned (Android offline choices per item, share target, quick capture). Server accounts for several people (1.7) and sharing with other people's devices (1.6) stay where they are: this plan is only the same person's own devices.

## Questions for the owner before 0.5.0 starts

1. Should sync be off until switched on (the plan), and should the first sync always ask before it changes anything?
2. Should a device that is paired be allowed to sync automatically whenever it appears, or only when you press the button?
3. Does the home server need to be reachable from outside the house (Tailscale only, or also an open port)? The plan assumes Tailscale and the home network only.
4. Does your girlfriend get her own separate vault on the server? That decides whether the server needs more than one vault in 0.5.5, or only in 1.7.
