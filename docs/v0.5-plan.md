# Version 0.5 plan: sync between your own devices

Written 2026-11-13 at the owner's request. The owner wants two devices of the same person to be connected in 0.5, preferably the way LocalSend works (devices on the same network see each other, and nothing needs a server), with a home server as the fallback.

## The idea in one paragraph

There is **one sync engine**, and it works between two devices that are both on. A "device" is the desktop or phone app, or a small always-on program on the home server. The server is not a different system: it is a device that never sleeps, so the same protocol, the same checks and the same tests cover every case. Two apps on the same Wi-Fi find each other like LocalSend does and sync directly. When one of them is the home server, the others reach it by typed address (home network or Tailscale) and the server keeps a copy while the laptop and phone are off.

## Can a LocalSend-style sync be done? Yes, with these limits

| Question | Answer |
|---|---|
| Windows and Linux app finding each other | Yes. The Rust side can send and listen for a small multicast announcement on the local network and run a small HTTPS server. Windows will ask once to allow the app through its firewall. |
| Android app finding other devices | Yes, but it needs a native piece (Android only lets an app hear multicast when it holds a "multicast lock"). That Kotlin code can only be compiled by CI, so it is tried on the real phone and tablet before 0.5 is called done. |
| Android syncing in the background | Not reliably. Android stops background work to save battery. In 0.5 the phone syncs while the app is open, and on a button press. Sync while the app is closed is a later improvement. |
| The browser client | It cannot find devices and cannot listen, so it can only talk to a home server (or a desktop app) at an address you type. It is not part of 0.5 any more (owner's decision, 2026-11-17); it comes in a later release with no number yet. |
| Wi-Fi that blocks devices from seeing each other (guest networks, some routers) | Discovery fails there. The fallback is typing the other device's address and port, which also works over Tailscale. |
| Both devices on at the same time | Required for direct sync. If the other one is off, nothing happens and nothing breaks; it syncs when both are on again. The home server removes this limit. |

## What stays the same

- Notes stay plain markdown files in an ordinary folder that Obsidian can open. SQLite or any index is only a cache that can be rebuilt.
- Nothing received from another device is trusted: size limits, nothing executed, paths checked so a file can never land outside the vault, and a damaged answer changes nothing.
- Keys live in the system's secure storage, never in the vault, logs or repository.
- Every write to the vault is atomic. Killing the app in the middle of a sync must not corrupt a note.
- No personal data in the repository: tests use `alice` and `bob` and `example.local`.

## Decisions to record when the slices are built

- **Conflicts never lose text.** If the same note changed on two devices since the last sync, both versions are kept: the newer one stays as the note and the other is saved next to it as "Name (conflict, device, date).md". Nothing is merged silently.
- **Deleting is a move to the trash on the other device**, never a silent permanent delete.
- **Pairing uses a one-time code** shown on one device and typed on the other. After that the two devices pin each other's keys. A device that is not paired is never synced with.
- **What is synced:** pages, attachments, drawings (`*.canvas.json`), and the hidden `.scalenote` settings that belong to the notes (folder and page colours). Not synced: the device's own settings (theme, text size), page history, and the trash of another device. The page history and trash can be added later.

## The owner's answers (2026-11-14)

1. **Sync is on by default, with a switch in Settings to turn it off. The first sync with a device always asks before it changes anything. The program never does anything without telling the user.** What this means in the build:
   - "On" means the sync feature is allowed to work. Nothing is synced until a device has been paired on purpose, so a fresh install does nothing.
   - To keep "on by default" safe on other people's networks, the app only listens for other devices and only announces itself while at least one device is paired, or while the "Pair a device" screen is open. With no paired device it is silent on the network. This is the builder's choice to make the default safe; the owner can change it.
   - The first sync with a device shows what it would do (files to add, change, move to the trash, and conflicts) and waits for a yes. Nothing is changed before that.
   - Every later sync runs by itself but always shows what it did: a status line in the app while it runs and when it ends ("Synced with Bob's laptop: 3 changed"), calm messages when it fails, and a "Sync activity" list in the Sync tab with the last syncs. No sync is silent.
2. **A paired device syncs by itself when it has the app open. If that does not work, there is a "Sync now" button.** Android keeps to the same rule (the app open).
3. **The home server works on the home network and over Tailscale.** An open port to the internet is not part of 0.5; it can come later, after the security checks after v1.
4. **A second person gets their own vault on the same server.** So the server (0.5.5) holds several vaults from the start. Each vault is its own folder with its own list of paired devices and keys; a device paired with one vault cannot see or reach another. No accounts or sharing between vaults (1.6 and 1.7 stay as planned).

## Changes of 2026-11-17 (owner's decision)

- **The browser client is out of 0.5.** It moves to a later release with no number yet. Nothing else in 0.5 needs it: the home server is reached by typed address, and the apps pair with it the same way. The hardening and release slice is now **0.5.6** (it was 0.5.7).
- **25 more things are added to the releases still to come**, numbered (1) to (25) in the schedule above: 6 in 0.5.3, 6 in 0.5.4, 6 in 0.5.5 and 7 in 0.5.6. 0.5.0 to 0.5.2 are already built and get none. Everything that was planned before stays.
- **Why each one is in its release:**
  - 0.5.3 (sync): (1) the plan says no sync is silent; (2) Compare reuses the first-sync preview; (3) the preview and activity list name the device; (4) sync writes files while the app is open, so the app has to notice changes it did not make; (5) conflict copies would pile up without a screen; (6) this is the first release where notes leave the device.
  - 0.5.4 (Android): (7) phone and tablet screens; (8) Find is Ctrl+F only, so a phone without a keyboard has no find; (9) sync adds per-device settings that need a place of their own; (10) a phone moves between networks; (11) Android stops apps, and the user should land where they were; (12) gives the Android back gesture a use.
  - 0.5.5 (home server): (13) direct sync needs both devices on, and the tray keeps a computer reachable; (14) first release with a server, so the choices and their costs are shown; (15) the server holds several vaults, so folders need to be told apart and switched quickly; (16) a server and the power-cut tests raise the stakes; (17) jobs on the server can drop pages in, and add-only cannot damage anything; (18) a server shows which devices connected and which are on an old version.
  - 0.5.6 (hardening): (19) the device key is kept in a private file on Linux and Android for now, so a lock adds protection; (20) a release should say what it is; (21) there are enough shortcuts by now to list; (22) every screen gets tried at the smallest and largest size; (23) a known bug, and this release is the one tried on every device; (24) a release check needs tests that can be trusted; (25) Linux packages get checked before release.
- **Order inside a release.** The sync part of a release is built and tried first. The extras come after it. If the sync part is not solid, its extras move to the next release. The v0.5 release still waits until sync between two devices on the same network works perfectly.
- **Unchanged rules for the extras:** suggestions and similar features are opt-in (see DECISIONS.md, 2026-11-17), there is no central server, and nothing in them costs money.
